# Spike — #23, the in-face value declaration

A bounded evidence spike for [FINDINGS.md](FINDINGS.md) #23, run in an isolated worktree off `close-findings` (a1f5c10). Scope: settle the three unknowns the row names, and report what the answer does to #41 and #52. **No verdict is claimed here** — the adopt-or-rule decision is reserved for another reviewer ([CAMPAIGN.md](CAMPAIGN.md), Execution protocol). What follows is evidence plus a read.

Every claim below is labelled **DRIVEN** (I ran it and this is what happened) or **READ** (I read the code and this is what it says). Prototype code lives in `spike23/` and behind three off-by-default env gates (`RIP_INFACE_PIN`, `RIP_INFACE`, `RIP_INFACE_SUPPRESS`); with them unset the suite is unchanged — `test/lang/tsface.test.js` 151 pass, `test/toolchain/check.test.js` 33 pass under `RIP_EXTENDED=1 RIP_REQUIRE_TSC=1` (**DRIVEN**).

## The two implementation sites, and why the strip answer differs between them

The row says "a TS-only value declaration ahead of the hoist line" without saying who emits it. There are two places it can come from, and they give different answers to Unknown 1, so the spike drove both.

- **Emit-time (A).** The emitter emits the declaration itself, inside `this.b.tsOnly(...)`, re-emitting the first write's RHS through `capturedExprText`. The bytes land in `compile()`'s own `tsRegions`.
- **Consumer splice (B).** The declaration is spliced into the face by the consumer from pass-1's GENERATED bytes (`pinnable.valueGen`), exactly the way `buildProbe` already builds the probe file — pass 1 to get the spans, pass 2 with `pins` set to `typeof <minted>`, then the splice. The compiler's face and `tsRegions` are untouched.

B is what `rip check` and the editor already do shape-wise (they already recompile with pins), so it removes the probe file and the hover round trip and nothing else.

## Unknown 1 — the strip gate

**Verdict: the strip TRANSFORM admits it; the strip GATE, as written, refuses it; and the emit-time route additionally breaks byte-parity for a reason that has nothing to do with types.**

The transform is mechanical: `builder.tsOnly` records `[start, end)` spans as the face emits them and `stripFace` deletes them (**READ**, `src/builder.js:75`, `src/emitter.js:13658`). The shipping JS is not produced by stripping at all — it is an independent `compile(face:'js')`, which never enters the branch (**READ**, `src/compile.js:119`). So a TS-only value declaration cannot reach shipping bytes by construction; the risk the row names is entirely about the parity invariant.

### Route B — byte-identical

Driver: `spike23/strip2.mjs`, over `test/corpus`, `test/audit/corpus`, `examples`, `packages`, `src` — 220 `.rip` files × 3 runtime deliveries = 660 compiles.

| | result |
| --- | --- |
| `stripFace(in-face TS) === compile(face:'js')` | **660 / 660 byte-identical** |
| regions ascending, disjoint, in range | 660 / 660 |
| compiles carrying declarations | 156 (609 declarations) |

**DRIVEN.** The compiler's own `tsRegions` never change under B, so `test/lang/tsface.test.js` is untouched (**DRIVEN** — 151 pass).

### Route A — byte-parity breaks, and the shape rule fires

Driver: `spike23/strip.mjs` with the emitter prototype on (`RIP_INFACE_PIN=1`).

| configuration | byte-identical | mismatch |
| --- | --- | --- |
| prototype off (baseline) | 660 | 0 |
| prototype on | 651 | **9** (3 files) |
| prototype on, capture given a scratch temp allocator | 657 | **3** (1 file) |

**DRIVEN.** The mismatches are not type syntax leaking into JS — they are shipping identifiers renumbering. `capturedExprText` re-runs the real expression emitter, which reserves loop/chain temp names (`this.temps.used.add`, `freshTempName`'s counter), so the shipping emission's `_ref` becomes `_ref1`:

```
got : let _ref1, _ref2, newLength, oldLength;      # TS face, stripped
want: let _ref,  _ref1, newLength, oldLength;      # JS face
```

Scratch-isolating `this.temps` around the capture removes six of the nine and leaves three (a temp allocated *later* in the TS face than in the JS face). I did not chase the residue to its root; what the drive establishes is that **the capture is not state-free, and one obvious isolation is not enough** — a correct emit-time route needs the capture run against a fully isolated emitter, not a patched allocator. There is a second, structural re-entrancy hazard visible in the same prototype: a captured function-valued RHS re-enters `hoistLine` for its own inner scopes and mints nested declarations (**READ** of the prototype's own output, `spike23/diag.mjs` on `packages/app/stash.rip`).

Run against the repo's own gate, route A fails four tests (**DRIVEN**, `RIP_INFACE_PIN=1 RIP_INFACE_ISOLATE=1 bun test test/lang/tsface.test.js` — 147 pass, 4 fail):

```
error: unrecognized TS-only region shape in implicitcalls.rip: "const __rip_pin_0_a = double(4);"
error: unrecognized TS-only region shape in match.rip:         "const __rip_pin_0__ = 5;"
error: unrecognized TS-only region shape in singleline.rip:    "const __rip_pin_0_t1 = 1;"
(fail) TS directive comments > Sibling-run interaction: a multi-name hoist line DECLINES
```

That first class of failure is the gate doing its job: `REGION_SHAPES` exists so "an emission change cannot quietly reclassify code bytes as TS-only", and an in-face value declaration is precisely code bytes classified as TS-only. Admitting it on route A means adding a shape rule that relaxes the one guard written to forbid this, plus fixing the allocator perturbation. **That is invasive.** On route B nothing in the gate moves, because nothing in the compiler's face moves.

## Unknown 2 — scope resolution of the RHS

**Verdict: placement AFTER the hoist line, not ahead of it; 179 of 203 declarations (88%) resolve; the 24 that do not are recoverable without a static analysis, at a named cost.**

### Placement (DRIVEN, `spike23/t3-scope.ts` against tsc 7.0.2)

`typeof` is a legal FORWARD reference in a type position, so the declaration does not have to precede the hoist line — and putting it after strictly dominates:

| shape | result |
| --- | --- |
| `const __p0 = base + 1;` **above** `let base, x!: typeof __p0;` | **TS2448** Block-scoped variable 'base' used before its declaration |
| `let base2, y!: typeof __p1;` then `const __p1 = base2 + 1;` | **clean** |
| declaration after the hoist line, RHS reads a Tier-1 declare-in-place binding declared later | **TS2448** |
| declaration after the hoist line, RHS reads a block-local | **TS2304** |

The row's own spelling (ahead of the hoist line) is the worse of the two: it loses every RHS that reads a sibling hoisted name. Everything below uses after-the-hoist-line placement.

### The census (DRIVEN, `spike23/census.mjs`)

Method: for each `.rip` file, emit the TS face twice — once as it is today (no pins), once with the in-face declarations spliced — write both sets into two directories, run the repo's pinned tsc (`tsgoBinaryPath()` → `@typescript/typescript-darwin-arm64/lib/tsc`, **7.0.2**) over each set as a batch, and diff diagnostics by (file, code, message) with multiplicity. A diagnostic that is new AND lands on a declaration's own line is a declaration whose RHS did not resolve. Corpus: `test/corpus`, `test/audit/corpus`, `examples`, `packages`, `src`.

| | count |
| --- | --- |
| `.rip` files | 220 |
| files carrying pinnables | 52 |
| in-face declarations emitted | **203** |
| (a) RHS resolves at the declaration site | **179 (88.2%)** |
| (b) RHS does not resolve | **24 (11.8%)** — 30 diagnostics |
| new diagnostics elsewhere in the file | 67 |

The 24 failures split cleanly into the two classes the placement drive predicted: **TS2448 ×12** (the RHS reads a binding this scope declares later with Tier-1 declare-in-place — `i`, `bells`, `url`, `pathname`, `router`, `renderer`, `base`, `labels`, `add`, `cursor`, `readWord`) and **TS2304/TS2552 ×18** (the RHS reads a block- or loop-local, or a name from an inner block — `ctx`, `dateStr`, `formatStr`, `full`, `elt`, `part`, `file`, `ext`, `text`, `raw`, `path`, `key`, `params`). Neither class is the row's "constants dominate" framing exactly; the population is dominated by function-valued and object-valued writes, and what fails is not literal-vs-name but *where the name is bound*.

Two variations, driven, that did not help and are worth not re-trying: appending module-scope declarations at end-of-file instead (178 resolve, one worse); and `const` vs `let` for the minted binding (**identical** 179 either way, but `const` narrows primitives to literal types and costs 3 extra TS2322s downstream — hover shows `let a: 5` for `const`, `let b: number` for `let`; **use `let`**, which is also what the probe's own `let __rip_probe_…` produced).

### Why the probe route does not have this problem (READ)

`buildProbe` splices at `lineStartOf(text, p.stmtGen[0])` — the line of the first-write STATEMENT, in the write's own scope (`packages/vscode/src/pins.js:44`). Its RHS therefore always resolves. The in-face declaration cannot sit there, because the type has to be on the hoist line, above the first read. **This is the structural trade the whole finding turns on.**

### The fallback — and the honest correction to "no regression"

The row assumes a declined binding "simply gets no declaration" and keeps today's TS7034. Driven, the picture is better in one way and worse in another.

**DRIVEN** (`spike23/t4-degrade.ts`): if the declaration's own region is diagnostic-suppressed, a non-resolving declaration needs no static decline rule at all. `let __p3 = tmp * 2;` with `tmp` unbound types `__p3` as the error type, `w!: typeof __p3` becomes `any`, and every read of `w` — `w.toFixed(2)`, `v.anything.at.all` — passes. The only diagnostics in the file are the two TS2304s on the declaration lines themselves, which the suppression removes. So the graceful degradation is free; no free-name analysis is required.

**But it is not "the same TS7034 it has today."** Under `--strict` the same file still reports only those two suppressible TS2304s (**DRIVEN**) — the binding is *annotated*, so TS7034/TS7005 never fire. A declined binding therefore goes from "loudly implicit-any under strict" to "silently `any`". That is a real change in the strict dimension and belongs in whatever ruling is written, not in a footnote.

The suppression itself is the probe file's own doctrine applied in place: the probe file was deleted before the user saw it, and a minted in-face declaration's region is the same machinery. It is implemented in the prototype as a line-range filter in `rip check`'s pull loop (`RIP_INFACE_SUPPRESS=1`).

### What the loss actually costs, on the real artifact

`rip check --json` over `packages/x12 packages/print packages/time packages/csv`, probe route vs in-face route with suppression (**DRIVEN**, `spike23/diff.mjs`):

```
A(probe)=575  B(in-face)=575   only-in-A: 7   only-in-B: 7
```

The 7 only-in-A are diagnostics the probe produced on bindings the in-face route declined — `csv.rip:118/501/506` (`'rows' is possibly 'null'`, a `never[] | null` mismatch) and `time/test.rip:243/246/263`. Those are the 12% made concrete: real reports, lost.

The 7 only-in-B are two distinct new hazards:

- **TS2502 ×2, "'u' is referenced directly or indirectly in its own type annotation"** — the in-face declaration keeps the reference live, so a self- or mutually-referential RHS is circular. The probe route escapes this because the hover ANSWER is fed back as inert text; the cycle is broken by the round trip. This is the same circularity the #41 body names as the reason the "substitute the real binding name" ceiling is not free, arriving from the other side.
- **TS2322 ×5 on nullish first writes** (`Type 'null' is not assignable to type 'undefined'`) — `let __p = undefined` types as `undefined`, and `typeof __p` pins that. The probe declines these because tsgo HOVERS such a declaration as evolving `any` and `parseProbeHover` rejects `any`. **The in-face route has no equivalent escape hatch**; it would need a syntactic exclusion for nullish/empty first writes.

### How the two routes' coverage actually compares

The probe route's own success rate, measured on the real artifact (`RIP_PIN_STATS=1 rip check` over `packages examples test/audit/corpus test/corpus`, **DRIVEN**): **51 files, 194 candidates, 159 pinned — 82.0%.** The remaining 18% fall to `parseProbeHover`'s unusable-answer filter (no fence, `any`, truncation), and at least some of the 82% are *wrong* (#41's self-referential answer counts here as a success and is what publishes the TS2304).

So the in-face route's 88.2% is not a coverage regression against today — it is a coverage *improvement*, differently distributed. The two rates come from different instruments (tsc-as-oracle over the whole tree at `runtimeDelivery: 'none'` vs the probe's own filter over the import closure at `'inline'`), so the candidate totals differ slightly (203 vs 194); treat them as rates, not as a paired comparison.

## Unknown 3 — the hover alias

**Verdict: there is nothing to alias for structural types, and for nominal ones the fix is to NAME the class expression with the user's own binding name. A type alias does not work.**

Driven against real tsgo 7.0.2 over LSP (`spike23/hover.mjs` + `spike23/cases.mjs`, hover at the binding's hoist line, at a use inside a closure, and at an instance local; diagnostics pulled from the same session). Rendered strings, verbatim:

| candidate | at the binding | at a use in a closure | at an instance local | the diagnostic's message |
| --- | --- | --- | --- | --- |
| **today**, probe on a forward class | `let Box: any` | `let Box: () => any` | — | `TS2304 Cannot find name '__rip_probe_0_Box'` |
| **A** `typeof __rip_pin_0_Box`, anonymous class | `let Box: typeof __rip_pin_0_Box` | `let Box: new () => __rip_pin_0_Box` | `const b: __rip_pin_0_Box` | `does not exist on type '__rip_pin_0_Box'` |
| **B** same, minted decl names the class `class Box` | `let Box: typeof Box` | `let Box: new () => Box` | `const b: Box` | `does not exist on type 'Box'` |
| **C** `type Box = typeof __rip_pin_0_Box` in front | `let Box: typeof __rip_pin_0_Box` | `let Box: new () => __rip_pin_0_Box` | `const b: __rip_pin_0_Box` | `does not exist on type '__rip_pin_0_Box'` |
| **D** minted type alias `__rip_pin_0_Box$T` | `let Box: typeof __rip_pin_0_Box` | — | — | — |
| **E** object RHS | `let cfg: { host: string; port: number; }` | same | — | `does not exist on type '{ host: string; port: number; }'` |
| **F** function RHS | `let fmt: (n: any) => any` | same | — | — |
| **H** `new Widget()` RHS | `let w: Widget` | same | — | `does not exist on type 'Widget'` |

Three things fall out, all **DRIVEN**:

1. **The leak is confined to anonymous class expressions.** Objects, functions and instances of user classes print structurally or by the user's own name — no minted text reaches hover at all (E, F, H). Since components lower to class expressions, "class expression" means *classes and components*.
2. **Type aliases do not help** (C, D). TypeScript prints a class type by its declaration's symbol name, not through the alias, so wrapping the `typeof` changes nothing. This is the obvious first idea and it is dead.
3. **Naming the class expression is the whole fix** (B): emit `let __rip_pin_0_Box = class Box { … }` and every surface — declaration hover, use hover, instance hover, and the diagnostic message — reads `Box`. The inner name is scoped to the class body, where it denotes the same class, so a self-referential body still resolves correctly. The one residual oddity is `let Box: typeof Box` at the hoist line itself, which is machinery-free but reads strangely.

`const` vs `let` also belongs here: `const __p = 5` hovers the binding as `let a: 5` and draws TS2322 on any later write; `let __p = 5` hovers `let b: number`. **`let`** (candidate G, **DRIVEN**).

## #41 — does it dissolve?

**Yes for the defect the row is about; the vocabulary leak survives in a new place unless the class expression is named.** All **DRIVEN** with `rip check` against the real tsgo session.

| program | probe route (today) | in-face route + region suppression |
| --- | --- | --- |
| forward-rendered component (`Parent` renders `Child` declared below) | `1:1 TS2304 Cannot find name '__rip_probe_0_Child'` | **✓ No type errors** |
| forward-referenced class (`make = -> new Box()` above `Box = class`) | `1:1 TS2304 Cannot find name '__rip_probe_0_Box'` + the program's real `5:6 TS2339` | only the real `5:6 TS2339` |
| forward class with a genuine defect (`b.nope()`) | `1:1 TS2304` — **and the real defect is never caught** | `3:5 TS2339 Property 'nope' does not exist on type '__rip_pin_0_Box'` |

The third row is the important one. The probe route publishes a false error at 1:1 and misses the true one entirely; the in-face route catches the true one at the right position. But the message names the minted symbol — so #41's *false diagnostic* dissolves while #41's *vocabulary leak* migrates from the error position into the error text, and Unknown 3's named-class-expression fix is what closes it. Without suppression there is a second problem: the RHS is type-checked twice, so a diagnostic inside a pinnable's first write is reported once at its true position and once inside the minted declaration, where it anchors at 1:1 (**DRIVEN** — before suppression, the forward-class program reported `1:1 TS2339 Property 'n' does not exist on type '__rip_pin_0_Box'` beside the correct `5:6`). Region suppression is not cosmetic; it is load-bearing.

`check.test.js`'s #41 interim gate goes **red** under `RIP_INFACE=1 RIP_INFACE_SUPPRESS=1` (32 pass, 1 fail — **DRIVEN**), which is exactly the campaign's cue to invert it.

## #52 — what each architecture requires

`{ json: media } = { json: 'application/json' }` read by a hoisted `def`. **DRIVEN** that the shape yields an empty pinnable list today (`spike23/c.mjs` on `spike23/f52/destructured.rip` — `pinnables: []`), so admitting the name to the carrier set is step one either way.

Step two differs, and the four shapes were driven side by side through tsc (`spike23/t5-52.ts`):

| shape | non-strict | `--strict` |
| --- | --- | --- |
| (1) unpinned — today | clean | `TS7034` at the pattern + `TS7005` at the read |
| (2) **probe route as it stands** — the assign node's WHOLE value span, so the pin is `{ json: string }` | **TS2322 at the destructuring write itself** + `TS2339 'length' does not exist on type '{ json: string; }'` | same |
| (3) **in-face, binding through the pattern** — `let { json: __rip_pin_0_m2 } = { json: '…' }` | clean; the negative fires correctly (`TS2339 'nope' … on type 'string'`) | clean |
| (4) **in-face, element-level value span** — `let __rip_pin_1_m3 = 'application/json'` | clean | clean |

Shape (2) is worse than the row states: the whole-object pin does not merely mistype the read, it makes the *write* illegal (TS2322 at the destructuring). Both in-face shapes work.

The difference in what each architecture must build:

- **In-face route:** the declaration text is `let <pattern, minted name in the element slot> = <the existing whole-value bytes>;`. The pattern re-spelling can be done by the emitter, which holds the AST and already knows which element introduced the name — no new span plumbing, and shape (4)'s element-level value span is an optimization, not a requirement.
- **Probe route:** `buildProbe` has only generated text and two offsets, so the same re-spelling is string surgery on the pattern's generated bytes inside `pins.js` — or it needs the element-level value span that #52 asks for, which is the identifier-read row's shape again.

One correction to the row's parenthetical: `pinKey` is `${name}@${hash}` (**READ**, `src/emitter.js:2659`), so two siblings from one pattern get **distinct keys** even sharing a value hash. What sharing the hash actually costs is invalidation granularity — editing one element invalidates both siblings' pins — not a collision.

## Recommendation, its confidence, and what would change it

**Recommendation: adopt the in-face declaration, on the consumer-splice route (B), with `let` as the minted kind, placement after the hoist line, region diagnostic-suppression, a named class expression for nominal RHSs, and a syntactic exclusion for nullish first writes. Confidence: moderate-to-high on the mechanism, moderate on the net-benefit trade.**

What the evidence supports firmly:

- The strip gate is not the obstacle the row feared, provided the declaration is spliced rather than emitted — 660/660 byte-identical, compiler face untouched. The obstacle is real and substantial on the emit-time route, and it is a re-entrancy problem, not a type problem.
- Scope resolution costs 12% of the population, and the fallback for that 12% is free (region suppression) rather than needing a static free-name analysis.
- Coverage is not a regression: 88% in-face vs 82% probe, measured differently but on the same tree.
- #41's false diagnostic dissolves, and the route additionally catches a real defect the probe route never reached.
- Hover has an exact, driven fix, and it is not the type alias everyone reaches for first.
- The architecture is strictly simpler: no probe file written and deleted per file, no hover round trip per pinnable, no `parseProbeHover` markdown parsing, no async in the pin pass, and `pins.js` retires.

What the evidence says the adopter is buying:

- 7 real diagnostics lost and 7 gained on four packages of real code — near-parity, but the two sets are not the same code, and the losses are all "binding declined, reads unchecked".
- A strict-mode behaviour change: a declined binding is silently `any` where today it draws TS7034/TS7005. This is the one item I would put in front of a reviewer before anything else, because it trades a loud honest gap for a quiet one.
- Two new hazards with named mitigations — circular self-referential RHSs (TS2502) and nullish first writes (TS2322) — neither of which the probe route has, because feeding an inert hover string back is a kind of type firewall that the live reference gives up.

What would change the recommendation:

- If the strict-dimension silence is judged unacceptable, the route needs a decline rule after all (free-name resolution at the declaration site), and the cost estimate moves from "free fallback" to "a real analysis in the emitter" — at which point the probe's floor fix for #41 (a self-reference clause in `parseProbeHover`) looks cheaper for a while.
- If someone wants the emit-time route (A) for its own reasons — a single compile instead of two, or declarations that belong to `tsRegions` — the spike's answer is that it needs a genuinely isolated capture, and my first isolation attempt was insufficient. That is a different, larger piece of work, and it also requires relaxing `REGION_SHAPES`.
- If the 7 lost diagnostics turn out to be representative rather than incidental at a larger sample, the 12% non-resolving population is worth attacking directly before adoption — the TS2448 half (12 of 24) is recoverable by teaching the splice to place a declaration *below* the Tier-1 binding it reads, which the spike did not try.
